# 배정 알고리즘

배정 엔진은 `src/domain/allocation/`의 순수 함수입니다. 입력이 같으면 결과도 항상 같습니다. 모든 수치는 `allocation-policy.ts` 한 곳에 있습니다. 구현과 자동 테스트까지 끝났고, 실기기 성능은 아직 측정하지 않았습니다.

## 입력과 출력

```ts
planWeek({
  chores,      // 그 주 인스턴스: 점수, 담당 방식, 기존 담당자, 잠금, 상태
  members,     // 활성 구성원과 목표 비율
  metric,      // POINTS | TASK_COUNT
  history,     // 최근 4주 구성원별 목표 대비 부담
  today,       // 지난 날짜 보호용
  seed,
}) => PlanOk | PlanError
```

성공하면 일정별 담당자, 구성원별 요약(목표·실제 부담, 건수, 차이), 설명 코드, `seed`, `algorithmVersion`을 돌려줍니다.

실패 코드는 `INVALID_SHARES`(합이 100이 아님), `NO_AUTO_CANDIDATE`(자동 배정 가능한 사람이 없음)이며, 임의로 배정하지 않고 화면에서 해결 방법을 안내합니다.

## 절차

1. 일정을 **고정 집합**과 **자동 집합**으로 나눕니다. 고정은 FIXED, MANUAL, 잠금, 완료·건너뜀, 지난 날짜입니다.
2. 구성원별 현재 부담을 고정 집합으로 계산합니다.
3. 목표 부담을 구합니다. `전체 부담 × 목표 비율`에 지난 부담 보정을 더합니다.
4. 자동 집합에 대해 **후보를 여러 개 만듭니다.**
   - 2명이고 자동 일이 16개 이하면 모든 조합을 평가합니다.
   - 그 외에는 무거운 일부터 배정하되, 결과가 비슷한 사람 중 seed로 고르는 방식으로 후보 24개를 만들고(일 40개 초과 시 8개), 각 후보를 일 옮기기·맞바꾸기로 개선합니다.
5. **1차 선택:** 비율 편차가 최선에 가까운 후보만 남깁니다.
6. **2차 선택:** 그중 보조 비용이 낮은 후보를 남기고 seed로 하나를 고릅니다.
7. 결과를 요약하고 설명 코드를 붙입니다.

정렬 후 순차 배정만 쓰면 동점이 없을 때 항상 같은 결과가 나와 "다시 배정"이 의미 없어집니다. 후보 방식은 비율에 가까우면서 결과가 달라질 여지를 함께 확보합니다.

### 다시 배정

현재 결과를 넘기면 그것과 다른 후보를 고릅니다. 2차 기준에 맞는 다른 후보가 없으면 1차 범위까지 넓힙니다. 그래도 없을 때만 같은 결과와 `NO_ALTERNATIVE`를 돌려줍니다. 어떤 경우에도 비율 편차 범위는 벗어나지 않습니다.

## 비용

원문의 비용식은 항을 모두 더했지만, 이렇게 하면 범위를 넓게 잡을 때 보조 조건이 선택에 거의 영향을 주지 못합니다. 그래서 두 값으로 분리했습니다.

```text
비율 편차 = Σ (구성원별 목표 대비 비율 차이)²      최선 + 12 이내만 통과 (2명 기준 약 2.5포인트)

보조 비용 = 1.5  × 지난주와 같은 일을 같은 사람이 맡은 횟수
          + 0.75 × 하루 5점을 넘긴 부담
          + 1    × 무거운 일(4점 이상)이 연속된 날 수     최저 + 1 이내만 통과
```

보조 조건은 비율 범위를 통과한 후보 사이에서만 작동하므로 비율 목표를 넘어설 수 없습니다. 지난 부담은 비용 항이 아니라 3번의 목표 조정으로 반영합니다.

## 지난 부담 보정

- 최근 확정된 4주를 사용하고, 오래된 주일수록 가중치를 줄입니다(0.5배씩).
- 각 주의 목표는 그 주의 스냅샷을 씁니다.
- 부담 계산: DONE은 완료한 사람, TODO는 담당자, SKIPPED·CANCELLED는 제외.
- 보정량 상한은 이번 주 전체 부담의 20%입니다. 이력이 없으면 0입니다.

## 재배정

`canReassign()`이 참인 일정만 바꿉니다. AUTO, TODO, 잠금 아님, 오늘 이후여야 합니다. "다시 배정"은 새 seed로 실행하고, 화면에서 변경 전후를 보여 준 뒤 확정합니다. 완료된 일까지 다시 배정하는 기능은 넣지 않습니다. 필요하면 완료를 먼저 취소하면 됩니다.

## 공정성의 범위

- "공정"은 **서로 합의한 비율에 가깝게 나눈다**는 뜻이며, 객관적인 공정성을 보장한다는 뜻이 아닙니다.
- 일은 쪼갤 수 없고 고정 일이 있으므로 정확한 60:40이 안 될 수 있습니다. 목표와 실제 비율을 나란히 보여 줍니다.
- 순위, 벌점, "불공정", "게으름" 같은 표현을 쓰지 않습니다.

| 설명 코드 | 표시 문구 |
|---|---|
| `ON_TARGET` | 목표 비율에 맞춰 배정했어요. |
| `FIXED_DEVIATION` | 고정 담당 업무를 반영해 지민 58%, 지은 42%로 배정됐어요. |
| `INDIVISIBLE_DEVIATION` | 집안일을 똑같이 나눌 수 없어 지민 58%, 지은 42%로 배정됐어요. |
| `HISTORY_ADJUSTED` | 지난 일정의 부담을 고려해 조금 조정했어요. |
| `ZERO_SHARE_EXCLUDED` | 지은님은 0%로 설정되어 자동 배정에서 제외했어요. |
| `NO_ALTERNATIVE` | 지금 조건에서는 이 조합이 목표에 가장 가까워요. |
| `SINGLE_MEMBER` | 자동 배정할 수 있는 사람이 한 명이라 모두 배정했어요. |
| `UNASSIGNED_PRESENT` | 담당자를 정해야 하는 일이 2개 있어요. |

## 테스트

**고정 결과를 정답으로 두지 않고 성질을 검사합니다.**

- 고정·수동·잠금·완료·지난 날짜가 그대로 유지됨
- 같은 seed는 같은 결과. 후보가 있으면 다른 seed에서 다른 결과가 나올 수 있음
- 0%·비활성 구성원은 자동 배정 안 됨, 없는 담당자 없음
- 보고한 실제 비율이 실제 데이터와 일치함
- 원문 시나리오: 2인 60:40, 3인 50:30:20, 고정 혼합
- 시뮬레이션: 일 1~100개, 구성원 1~8명. 순수 랜덤보다 평균 편차가 작은지, seed에 따라 특정인에게 쏠리지 않는지 확인 (결과는 README Work Log)
- 성능: 저가 Android 실측은 단계 3에서 수행. `npm run simulate`로 개발 PC 수치를 볼 수 있습니다.
